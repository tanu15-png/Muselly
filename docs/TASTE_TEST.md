# Taste test implementation

The implemented scope is questionnaire input, image choices, private uploads,
validation, draft persistence, and onboarding completion. Gemini, Qloo, image
analysis, recommendations, and the final Style DNA dashboard are absent.
`/dashboard` is an explicitly labelled saved-state placeholder.

## Files

- `shared/taste-questions.json`: twenty stable question IDs, option IDs, stages,
  optional flags, selection limits, and image assignments. Q20 is optional
  city/region and country, shown in About You. Both Python and React consume
  this file; deploy the `shared/` directory alongside `backend/`.
- `frontend/src/components/TasteTest.jsx`: five-stage progress, one question
  at a time, background autosave, immediate Back/Continue/Skip, final validation,
  completed-state restoration, and editing with a “Jump to end” shortcut to the
  inspiration step. The shortcut preserves answers and background saves; final
  completion still validates all required answers and uploads.
- `QuestionCard.jsx`: reusable image cards, chips, palettes, OtherInput, tags,
  and location input, with native keyboard-operable buttons and inputs.
- `InspirationUploader.jsx`: multi-file browsing/drop, previews, transfer
  progress, server-save status, retries, replacements, and authenticated images.
- `frontend/src/styles/taste.css` and `frontend/public/images/taste/`: responsive
  Muselly tokens, original vector illustrations, and a generated outfit sheet.
  Asset provenance and its prompt are recorded beside the images.
- `frontend/src/lib/draftQueue.js`: serialized background saves that retain
  the latest complete pending draft, coalescing superseded writes.
- `frontend/src/App.jsx`, `lib/navigation.js`, `lib/supabase.js`: protected
  routing, placeholder navigation, authenticated binary reads and uploads.
  Authentication components and sign-in behavior are unchanged.
- `backend/app/onboarding.py`: authenticated endpoints and backend validation.
- `backend/app/models.py`, `config.py`, `main.py`, and
  `alembic/versions/0002_taste_test.py`: data models, storage configuration,
  routing and migration. `pyproject.toml`/`uv.lock` add Pillow and pytest import
  configuration.
- Backend/frontend tests, `.env.example`, README, setup guide and TODOs document
  and verify the behavior.

## Data and API

`muselly_taste_tests` stores the authenticated user ID, answers keyed by stable
question ID, cursor position, completion timestamp, and created/updated times.
Each answer contains `choices`, `other`, `text` (names), and `location` (Q20).
Optional blanks remain valid; incomplete Other answers may be saved as drafts,
but cannot pass Continue or completion.

`muselly_inspiration_images` stores image ID, user ID, internal storage path,
filename, MIME type, processed byte size, dimensions, and timestamps. A
successfully uploaded object must exist before its metadata is committed.
Completion revalidates required answers, the 5–10 count, and storage existence
using HEAD requests before writing `completed_at`.

- `GET/PUT /api/onboarding`: restore/save a draft.
- `PUT /api/onboarding/images/{uuid}`: upload or replace raw image bytes;
  `Content-Type` and URL-encoded `X-Filename` describe the file.
- `GET /api/onboarding/images/{uuid}`: authenticated, owner-only binary image.
- `DELETE /api/onboarding/images/{uuid}`: remove an owned image.
- `POST /api/onboarding/complete`: validate saved data and finish.

Each endpoint verifies Supabase authentication. Request bodies cannot supply a
user ID or completion status. PostgreSQL locks serialize mutations per user,
including the ten-image cap; blocking database/storage work runs in worker
threads. Storage paths are generated by the backend under the verified user's
UUID. No public URLs, signed URLs, browser storage permissions, or service-role
keys are exposed to the frontend. See [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

Retries reuse an image ID; replacements use a new storage path and only swap
metadata after success. The previous image survives failed replacements.
Removing below five images invalidates completion. Optional questions and
valid answer edits do not erase completed status or other saved data.

Upload validation checks extension, MIME type, actual image decoding, size,
pixel count, and animation. Images are re-encoded to strip EXIF/GPS metadata.
The frontend's transfer reaches 100% before the server finishes processing;
it then shows “Saving securely…” until storage and metadata both succeed.
Pending local files cannot survive a browser restart; successfully saved images
and questionnaire drafts do. The save status distinguishes saved and pending
answers; autosave runs after 600 ms. Back/Continue/Skip update the local quiz
immediately and enqueue the new draft without waiting for the database. Only
one save runs at a time; newer pending snapshots replace older ones because
each contains all answers. Save failures retain the draft and expose Retry;
continuing to answer also queues a fresh save. Finish waits for the latest
queued snapshot to save before requesting completion.

## Setup

1. Run `uv sync` in `backend/` to install Pillow.
2. Set `SUPABASE_SECRET_KEY` in `backend/.env` to the project's secret
   key (`sb_secret_...`), then restart the backend. The legacy service_role JWT
   also works via `SUPABASE_SERVICE_ROLE_KEY`. Never use a `VITE_` variable.
3. Run `uv run alembic upgrade head` in `backend/`. Revision `0002_taste_test`
   creates two application tables, RLS/grants, and a private bucket in Supabase.
   It leaves existing profiles and legacy selected aesthetics intact.
4. Build/run the existing frontend. No new frontend variables or services.

Object Storage and PostgreSQL do not share a transaction. Failed DB writes
attempt to remove newly uploaded objects; old replacement files are cleaned up
on a best-effort basis. A cleanup failure can leave a private, unreferenced
object; production housekeeping should remove such objects. Account deletion
should remove storage objects before deleting the application profile (the
metadata foreign keys cascade; Storage files do not).

## Verification

Automated tests use temporary migrated SQLite databases and mocked Supabase
Auth/Storage, plus React DOM interaction tests. They cover the full twenty-
question journey, draft refresh, Back, optional skip, location, Other, tags,
selection limits, exclusive dislikes, malformed inputs/files, supported types,
size and count limits, upload failure/retry, replacement at capacity, deletion,
completion, saved returning users, missing storage objects, and owner isolation.
Migration upgrade/downgrade and SQLAlchemy metadata consistency are tested.

Live Supabase migration `0002_taste_test` was applied during implementation.
Read-only checks confirmed the bucket is private, the tables have RLS enabled,
and browser roles cannot read them directly. A live image round-trip attempt
was blocked because the supplied storage key was a public/anon JWT; temporary
test database records were removed. Set the actual secret or service_role key
before live acceptance. The API detects this configuration mix-up explicitly.

Chromium checks passed at 375, 768, 1024, and 1440px for six layouts (24 checks),
with no horizontal overflow. They also verified keyboard Space/Enter selection,
five-image upload/completion, and the signed-out redirect using mocked API
responses. Screenshots and checks are in ignored `test-results/taste/`.
Frontend tests: 24 passing, including slow writes, coalesced pending drafts,
failed-save recovery, and waiting for saving before completion. Backend tests: 28 passing (one existing dependency
deprecation warning). Production build: passing. Backend tests include
both modern secret and legacy service-role handling, with anon rejection.
Responsive checks do not certify real Supabase email/Google authentication or
live Storage credentials. Remaining live acceptance is tracked in `todos.md`.
